# Module M8.7 — Production Monitoring Reliability, Recovery, Concurrency, Auditability & Operational Validation

## 1. Executive Summary

Module **M8.7** solidifies the Tamil Nadu Forest Monitoring & Environmental Enforcement System's satellite monitoring pipeline into an enterprise-grade, continuous production monitoring infrastructure. Building directly on the real Google Earth Engine ingestion and incremental processing foundations of **M8.1 through M8.6**, M8.7 guarantees operational resilience, deterministic concurrency handling, transient network fault tolerance, automated recovery of interrupted/stale executions, and comprehensive auditability without mutating existing business calculations or permanent zone baselines.

---

## 2. Core Capabilities & Architecture

### 2.1 Atomic Concurrency Guard & Idempotency
- **Distributed Worker Protection**: Uses atomic MongoDB `findOneAndUpdate` with composite indexing (`{ areaId: 1, targetObservationId: 1 }`) to ensure simultaneous scheduling triggers or parallel worker instances never duplicate processing or double-charge GEE quota.
- **Idempotency Guarantee**: If an observation has already completed or is currently processing, concurrent requests atomically return the active/completed record without re-reduction or redundant alert emissions.

### 2.2 Transient vs. Permanent Error Classification & Bounded Retries
- **Error Classifier (`classifyError`)**:
  - **Transient / Retryable**: Network timeouts (`ETIMEDOUT`, `ECONNRESET`), HTTP 429 rate limiting, HTTP 503/504 gateway and service outages, transient MongoDB network errors. These transition to `RETRY_PENDING` with exponential / configured backoff (`nextRetryAt`) up to `maxRetries = 3`.
  - **Permanent / Non-Retryable**: Coordinate validation failure (`badValue`, invalid polygon geometry), collection schema mismatch, sensor track mismatch (`SENSOR_TRACK_MISMATCH`). These transition immediately to `FAILED` with `isPermanentFailure = true`.
- **Manual Retry API**: `POST /api/monitoring/retry/:jobId` allows authorized administrators to re-queue failed jobs once underlying external constraints are resolved.

### 2.3 Stale Job Recovery & Execution Resumption
- **Interruption Detection**: Scans active execution states (`QUEUED`, `ACQUIRING`, `REDUCING`, `PROCESSING`, `CHANGE_ANALYSIS`, `ALERT_EVALUATION`) stuck longer than the configurable stale threshold (`default: 5 minutes`).
- **Autonomous Recovery (`recoverStaleJobs`)**:
  - If `retryCount < maxRetries`: Automatically resets state to `RETRY_PENDING` and increments retry counter.
  - If `retryCount >= maxRetries`: Marks job permanently `FAILED` with error code `STALE_EXECUTION_TIMEOUT`.

### 2.4 Temporary Workspace Cleanup Guarantee
- **Zero Disk Leakage (`TempImageManager.withTemporaryWorkspace`)**: Executes all image tile manipulations and temporary raster rasters in dedicated per-job subdirectories wrapped in deterministic `try...finally` cleanup blocks. Even on unhandled runtime exceptions or abrupt timeouts, 100% of temporary files and folders are purged from disk.

### 2.5 Permanent Zone Baseline Protection & Temporary Area Isolation
- **Strict Baseline Isolation**: Temporary marked areas (e.g. mining investigations, rapid clearings) execute ad-hoc change detection against historical satellite observations without creating, mutating, or overwriting active permanent zone baselines (`BaselineModel`).
- **Temporal Lifecycle Enforcement**: Temporary areas that have passed their expiration date or analysis window (`endDate`) are automatically excluded from subsequent discovery cycles.

### 2.6 Operational Health Check & Audit Telemetry
- **Health Diagnostic Endpoint (`GET /api/monitoring/health`)**:
  - Database connectivity and state.
  - Google Earth Engine authentication status and verified satellite collections.
  - Incremental job queue depth (pending, processing, stale, failed, retry pending).
  - Total active monitored permanent and temporary zones.
- **Structured Audit Trails**: Every state transition (`DISCOVERED -> QUEUED -> ACQUIRING -> REDUCING -> PROCESSING -> CHANGE_ANALYSIS -> ALERT_EVALUATION -> COMPLETED / FAILED / RETRY_PENDING`) logs ISO-timestamped audit entries with automatic redaction of bearer tokens, API keys, and private credentials.

## 3. API Endpoints

| Method | Path | Auth / Role | Description |
|---|---|---|---|
| `GET` | `/api/monitoring/health` | `SUPER_ADMIN`, `ADMIN`, `DISTRICT_OFFICER`, `MONITORING_OFFICER` | Detailed operational health check of DB, GEE, queue metrics, and active area counts. |
| `POST` | `/api/monitoring/recover-stale` | `SUPER_ADMIN`, `ADMIN` | Manually triggers stale job scan and recovery for stuck operations. |
| `POST` | `/api/monitoring/retry/:jobId` | `SUPER_ADMIN`, `ADMIN`, `DISTRICT_OFFICER`, `MONITORING_OFFICER` | Re-queues a failed incremental monitoring job. |
| `GET` | `/api/monitoring/status` | Authenticated Users | Aggregated operational KPI metrics. |
| `GET` | `/api/monitoring/areas` | Authenticated Users | Area-level monitoring status breakdown with last processed dates. |
| `GET` | `/api/monitoring/incremental-jobs` | Authenticated Users | Filterable paginated list of incremental monitoring jobs. |
| `POST` | `/api/monitoring/run-cycle` | `SUPER_ADMIN`, `ADMIN`, `DISTRICT_OFFICER`, `MONITORING_OFFICER` | Triggers a full automated multi-area incremental monitoring cycle. |
