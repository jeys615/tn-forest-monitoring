### A. EXECUTIVE SUMMARY

A forensic audit of the optical satellite monitoring, image processing, change detection, and visualization subsystem was executed across the entire codebase (`server`, `client`, `shared`, database models, services, repositories, controllers, routes, providers, and test suites) and existing stored artifacts on disk and in MongoDB.

#### Key Forensic Findings:
1. **Optical Change Detection is Not Pixel-Level:**
   In [`ChangeDetectionService.ts`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/ChangeDetectionService.ts#L347-L375) and [`OpticalChangeDetector.ts`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/changeDetection/OpticalChangeDetector.ts#L118-L129), optical change detection **never loads local raster files, never harmonizes spatial grids, and never compares pixel arrays**. Instead, it subtracts single scalar mean index values ($\Delta\text{NDVI}$, $\Delta\text{BSI}$, $\Delta\text{NDBI}$), computes a scalar composite delta, and synthesizes a synthetic changed pixel count using an arbitrary multiplier:
   $$\text{changedPixels} = \text{Math.round}(\text{compositeDelta} \times 4000.0)$$
   This heuristic calculation is stamped with `calculationMode: REAL` and `spatialSource: RASTER`, presenting a non-spatial heuristic estimate as genuine raster analysis.
2. **Harmonization in Pipeline B is Image Resizing, Not Geospatial Reprojection:**
   In [`RasterHarmonizationService.ts`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/raster/RasterHarmonizationService.ts#L28-L58), the function `harmonizeToBaselineGrid` performs continuous array stretching using scale ratios ($\text{scaleX} = \text{srcW} / \text{targetW}$, $\text{scaleY} = \text{srcH} / \text{targetH}$). It ignores geographic coordinates, bounding boxes, affine transforms, and CRS definitions. If the source image is in UTM Zone 43N and the target is in UTM Zone 44N, it stamps `crs: targetGrid.crs` onto the array without coordinate reprojection.
3. **Cross-Sensor Comparison Without Normalization:**
   [`ChangeDetectionService.ts`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/ChangeDetectionService.ts#L150) only checks `sensorType !== refSensorType` (`OPTICAL` vs `SAR`). It allows direct comparisons between **Landsat-8** ($30\text{ m}$, UTM 44N) and **Sentinel-2** ($10\text{ m}$, UTM 43N) without cross-sensor radiometric calibration or spatial alignment. In `CHG-1790510572230-4759` (Vadipatti), comparing an 11-year-old Landsat-8 baseline with a Sentinel-2 image produced a false-positive **16.022% affected area** and triggered a **HIGH severity alert** (`ALT-1790510572230-8843`).
4. **Pixel-Level Cloud Masking is Inoperative:**
   Although [`RasterPreprocessingService.ts`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/raster/RasterPreprocessingService.ts#L38-L47) contains an `if (raster.qa)` branch for Sentinel-2 SCL masking, [`GeeExportService.ts`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/gee/GeeExportService.ts#L80-L83) explicitly strips `SCL` and `QA_PIXEL` from export tasks to avoid GeoTIFF type errors. All optical GeoTIFFs on disk contain only 6 reflectance bands; `raster.qa` is always `undefined`, rendering pixel-level cloud masking inoperative.
5. **Curtain Slider Visual Registration is an Illusion:**
   [`SatelliteImageViewerModal.tsx`](file:///d:/tn-enforcement-system/tn-forest-monitoring/client/src/components/satellite/SatelliteImageViewerModal.tsx#L712-L749) renders raw, un-harmonized PNGs for optical comparisons. For cross-sensor cases like Vadipatti, it places a $314 \times 236$ Landsat PNG under a $2569 \times 2237$ (or $930 \times 717$) Sentinel-2 PNG. CSS `maxWidth: 100%` stretches both into the container, creating an illusion of alignment over fundamentally mismatched spatial footprints.

#### Detailed Execution Answers:
- **A. Where are baseline and current rasters loaded?**
  - **In Pipeline A (`ChangeDetectionService`):** Rasters are **not loaded**. Only scalar numbers stored in `ProcessedImageResult.opticalMetrics` are used.
  - **In Pipeline B (`MonitoringSchedulerService`):** Loaded via [`RasterReaderService.readOpticalRaster`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/raster/RasterReaderService.ts#L38) using `GeoTiffService.readGeoTiff`.
- **B. Are they loaded as actual raster arrays?**
  - In Pipeline A: No.
  - In Pipeline B: Yes (`Float32Array` band arrays).
- **C. Which service performs spatial harmonization?**
  - In Pipeline A: None.
  - In Pipeline B: [`RasterHarmonizationService.ts`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/raster/RasterHarmonizationService.ts#L16).
- **D. Is there an actual reprojection operation?**
  - **No.** Neither pipeline calls coordinate transformations or geodetic reprojections for optical imagery.
- **E. Is there actual resampling?**
  - In Pipeline A: No.
  - In Pipeline B: Bilinear interpolation is performed across raw array indices, but without georeferenced coordinate mapping.
- **F. What CRS is used for the analysis?**
  - In Pipeline A: None (the database field `analysisGrid` is `undefined`).
  - In Pipeline B: It copies the string `baseRawRaster.metadata.crs` without transforming the coordinates.
- **G. How is the analysis grid selected?**
  - There is no analysis grid for optical change detection.
- **H. How are origin, pixel size, width, height, and affine transform determined?**
  - They are not determined for optical change detection.
- **I. Is the grid deterministic?**
  - Since no canonical analysis grid is constructed, determinism is absent.
- **J. Are both rasters warped onto exactly the same grid?**
  - **No.**
- **K. Is the zone polygon rasterized against that grid?**
  - **No.**
- **L. Is the valid comparison mask `baselineValid AND currentValid AND zoneMask`?**
  - **No.** In Pipeline A, `validPixels` is estimated from zone area: `validPixels = (zoneAreaHectares * 10000) / pixelAreaM2`. In Pipeline B, it is `baselineValidMask[i] === 1 && currentValidMask[i] === 1`.
- **M. Are NoData values correctly excluded?**
  - In Pipeline A: NoData pixels are not processed since raw rasters are bypassed.
  - In Pipeline B: Checked via `isNaN` in unaligned coordinate spaces.
- **N. Are pixels outside the intersection excluded?**
  - **No.** Since the two rasters are not co-registered on a shared coordinate grid, no spatial intersection mask exists.
- **N.1 Is the valid comparison area calculated from actual raster coverage?**
  - **No.** It is derived from the nominal `zone.areaHectares` database attribute.

#### Forensic Findings:
1. **Zero Coordinate Grounding:**
   The function calculates resampling coordinates using array indices:
   $$x_{\text{src}} = x_{\text{dest}} \times \frac{W_{\text{src}}}{W_{\text{dest}}}, \quad y_{\text{src}} = y_{\text{dest}} \times \frac{H_{\text{src}}}{H_{\text{dest}}}$$
   It **never converts array indices $(x, y)$ to geographic coordinates $(X_E, Y_N)$**.
2. **Missing Affine Transforms:**
   No geotransform or affine matrix ($\begin{bmatrix} a & b & c \\ d & e & f \end{bmatrix}$) is used. Differences in scene corners, pixel shifts, or spatial offsets are ignored.
3. **No CRS Reprojection:**
   There is no map projection transformation (such as Proj4 or GDAL warp). If `currentRaster` is in `EPSG:32643` (UTM 43N) and `targetGrid` is in `EPSG:32644` (UTM 44N), the function sets:
   ```typescript
   crs: targetGrid.crs,
   normalizedCrs: targetGrid.crs,
   ```
   This is an invalid metadata re-labeling: it relabels an array from one coordinate reference system into another without moving or projecting any pixels.
4. **Classification:**
   This operation is **IMAGE RESIZE / DIMENSION MATCHING**. It is **not** a geospatial warp.

### G. CROSS-SENSOR AUDIT

In [`ChangeDetectionService.ts`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/ChangeDetectionService.ts#L150-L155):

if (sensorType !== refSensorType) {

The system checks that both are `OPTICAL`, but **does not check if one is Landsat and the other is Sentinel-2**.

When `baseline.source !== current.source`:
- It does **not** reject cross-sensor pairs.
- It does **not** harmonize spatially.
- It does **not** perform spectral bandpass translation.
- It calculates single scalar mean indices, subtracts them, multiplies by 4000, and reports change.

> [!CAUTION]
> **CLASSIFICATION: CRITICAL_PRODUCTION_RISK**  
> Direct subtraction of un-normalized Landsat-8 and Sentinel-2 observations generates false alarms due to sensor spectral response, resolution, and atmospheric processing differences.

### J. SPECTRAL INDEX AUDIT

Formulas implemented across the two pipeline components:

| Index | Target Phenomenon | Pipeline A Formula ([`OpticalImageProcessor.ts`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/imageProcessing/OpticalImageProcessor.ts)) | Pipeline B Formula ([`PixelAnalysisService.ts`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/raster/PixelAnalysisService.ts)) | Input Source |
| :--- | :--- | :--- | :--- | :--- |

| **NDWI** | Water/Moisture | $(\overline{\text{NIR}} - \overline{\text{SWIR1}}) / (\overline{\text{NIR}} + \overline{\text{SWIR1}})$ *(Gao)* | $(\text{GREEN}_i - \text{NIR}_i) / (\text{GREEN}_i + \text{NIR}_i)$ *(McFeeters)* | **Inconsistent definitions** |

| **BSI** | Bare soil exposure | $\frac{(\overline{\text{SWIR1}}+\overline{\text{RED}}) - (\overline{\text{NIR}}+\overline{\text{BLUE}})}{(\overline{\text{SWIR1}}+\overline{\text{RED}}) + (\overline{\text{NIR}}+\overline{\text{BLUE}})}$ | $\frac{(\text{SWIR1}_i+\text{RED}_i) - (\text{NIR}_i+\text{BLUE}_i)}{(\text{SWIR1}_i+\text{RED}_i) + (\text{NIR}_i+\text{BLUE}_i)}$ | Summary mean vs Pixel array |
| **SAVI** | Soil-adjusted veg | $(1 + L)\frac{\overline{\text{NIR}} - \overline{\text{RED}}}{\overline{\text{NIR}} + \overline{\text{RED}} + L} \;(L=0.5)$ | $(1 + L)\frac{\text{NIR}_i - \text{RED}_i}{\text{NIR}_i + \text{RED}_i + L} \;(L=0.5)$ | Summary mean vs Pixel array |
| **EVI** | Enhanced veg | $2.5\frac{\overline{\text{NIR}} - \overline{\text{RED}}}{\overline{\text{NIR}} + 6\overline{\text{RED}} - 7.5\overline{\text{BLUE}} + 1}$ | $2.5\frac{\text{NIR}_i - \text{RED}_i}{\text{NIR}_i + 6\text{RED}_i - 7.5\text{BLUE}_i + 1}$ | Summary mean vs Pixel array |

#### Mathematical Flaw in Pipeline A:
Evaluating spectral indices on zonal means violates Jensen's Inequality:
$$\frac{\mathbb{E}[\text{NIR}] - \mathbb{E}[\text{RED}]}{\mathbb{E}[\text{NIR}] + \mathbb{E}[\text{RED}]} \ne \mathbb{E}\left[\frac{\text{NIR} - \text{RED}}{\text{NIR} + \text{RED}}\right]$$
Averaging non-linear ratios produces mathematically distorted indices.

### K. PIXEL-LEVEL CHANGE DETECTION AUDIT

In [`OpticalChangeDetector.ts`](file:///d:/tn-enforcement-system/tn-forest-monitoring/server/src/services/changeDetection/OpticalChangeDetector.ts#L118-L129):

### M. MULTI-INDEX LOGIC AUDIT

In `OpticalChangeDetector.ts`:
$$\text{compositeDelta} = \frac{1.5 \times \max(0, -\Delta\text{NDVI}) + 1.2 \times \max(0, \Delta\text{BSI}) + 1.0 \times \max(0, \Delta\text{NDBI})}{3.0}$$

- The three indices are combined into a weighted average.
- If negative vegetation change is zero ($\Delta\text{NDVI} \ge 0$), but soil moisture changes cause $\Delta\text{BSI} = +0.05$ and $\Delta\text{NDBI} = +0.04$, `compositeDelta` evaluates to:
  $$\frac{0 + 1.2(0.05) + 1.0(0.04)}{3.0} = \frac{0.10}{3.0} \approx 0.0333$$
- This yields synthetic changed pixels, even in the absence of canopy loss.
- **Flaw:** A shift in soil index can trigger an alert without verified vegetation disturbance.

### T. ROOT CAUSES

1. **Architectural Disconnect:**
   Pipeline B (`PixelAnalysisService`, `RasterHarmonizationService`, `RasterReaderService`) was developed as an experimental raster prototype, while production change detection (`ChangeDetectionService`) remained attached to Pipeline A (`OpticalChangeDetector`), which relies on summary metrics.
2. **Missing Optical Reprojection Engine:**
   When spatial harmonization was implemented for SAR (`reprojectSarToGrid`), the optical pipeline was not upgraded to use `AnalysisGridService` or `CrsTransformService`.
3. **Band Type Limitations in GEE Export:**
   GEE's `Export.image.toDrive` rejects exports with mixed data types (UInt16 reflectance alongside Byte SCL). Rather than casting SCL/QA to UInt16, the export service stripped the quality bands entirely, removing the source data required for pixel-level cloud masking.
4. **Permissive Sensor Verification:**
   The validation check in `ChangeDetectionService.ts` evaluated only `sensorType` (`OPTICAL === OPTICAL`), allowing disparate satellite platforms (Landsat vs Sentinel-2) to be compared without cross-sensor normalization.

> [!NOTE]

1. **Centralized Optical Compatibility Engine (`OpticalCompatibilityService`):**
